# Plan: CI on GitHub Actions with size-limit (MY-183)

Goal: GitHub runs the same checks as the local gate on every push, so a commit that skipped the
pre-commit hook (`--no-verify`, a web edit) still cannot land a lint error, an unformatted file, a
broken build or a heavier bundle unnoticed, and a task branch gets CI before the local merge. No
spec: nothing the site does or shows changes.

## Workflow

One file, `.github/workflows/ci.yml`, one job on `ubuntu-latest`, the same shape as the author's
other project's workflow, with npm in place of yarn:

- Trigger: `push`, every branch. No `pull_request`: pull requests are not used
  (`local-merge-without-pr`), and a branch push already runs the checks.
- `permissions: contents: read`; `concurrency` per ref with `cancel-in-progress`, so a newer push
  replaces a running one; the job has a `name`.
- `env: HUSKY: 0`: `npm ci` runs `prepare` (`husky`), and CI has no hook to install.
- `actions/checkout@v7`, `actions/setup-node@v7` with `node-version: 22` and `cache: npm`. `engines`
  is a range that `setup-node` would resolve to the newest Node; `size-limit` needs 22.19 or newer,
  which the latest 22 satisfies.
- `npm ci`, then `npm run lint`, `npm run lint:css`, `npm run format:check`, `npm run build`,
  `npm run size`, each its own step so a failure names the check.
- `format:check` passes on Linux because of `endOfLine: "auto"` (`line-endings-auto`).
- Action majors are pinned (`@v7`, the current majors); no comments, matrix or extra jobs.

## size-limit

Dev dependencies: `size-limit` and `@size-limit/file` only. The `file` plugin measures built files
as they are, which is all we need: no bundler preset (`webpack`, `esbuild`), so no second build.
Script `size`: `size-limit`, run after `npm run build`. Config `.size-limit.json`, one object per
limit (comments are not allowed in JSON; the reasoning goes into the decision record).

Numbers from a build of `main` (gzip for text, raw for the font and images, already compressed):

| Entry                        | Path                        | Now     | Limit  |
| ---------------------------- | --------------------------- | ------- | ------ |
| JavaScript                   | `dist/assets/*.js`          | 1.3 kB  | 3 kB   |
| CSS                          | `dist/assets/*.css`         | 3.4 kB  | 5 kB   |
| Font                         | `dist/assets/*.woff2`       | 39.7 kB | 45 kB  |
| Raster images (decor, photo) | `dist/assets/*.{avif,webp}` | 91.5 kB | 120 kB |

The margin is roughly a third to a half over today for JS, CSS and images: enough for the CSS and
JS refactors that run next and for a section or two, tight enough that an unoptimised photo or a
per-dot vector decor (`light-decor-raster`) fails the check. The font gets a small margin: a second
face or weight is the author's decision (`assets-performance`), and this makes it visible. The images
are one total rather than a first-screen subset: the decor and the Careers photo are the only rasters,
and a total does not need updating when a section moves its image. SVG icons are not limited: a few
hundred bytes each.

## Verification

- Locally: `npm run lint`, `npm run lint:css`, `npm run format:check`, `npm run build`,
  `npm run size`; a deliberately lowered limit makes `npm run size` exit non-zero, then it is
  restored.
- The branch `my-183-ci` is pushed (not `main`); the push itself runs the workflow, and the run is
  read through the public API and must be green.
